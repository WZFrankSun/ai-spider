本文件被拆成若干个**可独立发送的模块**。每次只把一个模块发给 Codex，让它单独完成、单独验证、单独提交，然后再发下一个。

模块顺序有依赖，**必须按顺序执行**：

每个模块的通用要求见第 1 节；每个模块的末尾有「本模块完成标志」，供 Codex 自检。

# 模块 M1：邮编规范化与比对工具

## 目标

新增一个独立的工具模块，提供「邮编规范化」和「页头文本中是否包含目标邮编」的判断能力，解决英国站邮编 `SW1A 1AA` 在 Amazon 页面上显示为 `SW1A1AA` 时被误判为「配送未生效」的问题。

## 背景

当前页头回读用正则匹配：

```
SW1A 1AA  →  SW1A + \s+ + 1AA
```

`\s+` 要求两段之间**至少有一个空白字符**。Amazon 在英国站实际显示 `SW1A1AA`（无中间空格），因此正则匹配失败，扫描判定「未观察到请求的配送邮编」，把正常配送误报为技术故障。

同时，正则还无法处理零宽字符（Amazon 某些页面会在字符间插入 U+200B~U+200F、U+FEFF），这些字符不可见但会让匹配失败。

## 改动内容

### 新增文件：`app/monitoring/config/postal_codes.py`

提供三个函数：

### 函数一：`normalize_postal(value)` —— 规范化单个邮编

处理步骤（**顺序固定**）：

1. 如果传入 None 或空字符串，返回空字符串。
2. 移除所有空白字符（空格、制表符、换行、全角空格）。
3. 移除所有连字符（`-`）。
4. 移除零宽字符：U+200B、U+200C、U+200D、U+200E、U+200F、U+FEFF。
5. 移除软连字符 U+00AD。
6. 转大写。
7. 去掉首尾空白。

### 函数二：`postal_matches(readback, target)` —— 页头文本是否包含目标邮编

- 先对 `readback` 和 `target` 都做规范化。
- 把规范化后的 `readback` 按「非字母数字」字符切分成 token 列表。
- 判断 token 列表中是否存在某个 token 等于规范化后的 `target`。
- 返回布尔值。

**为什么用 token 相等而不是子串包含**：防止「目标 `10115` 错误匹配到 `101150`」这类部分匹配。

**必须满足这些行为**：

| 目标 | 读回文本 | 结果 |
|---|---|---|
| `SW1A 1AA` | `Lieferung nach London SW1A1AA` | 匹配 |
| `SW1A 1AA` | `Lieferung nach London SW1A 1AA` | 匹配 |
| `SW1A 1AA` | `Lieferung nach London SW1A‌1AA`（含零宽字符） | 匹配 |
| `SW1A 1AA` | `Lieferung nach London SW1A1AB` | 不匹配 |
| `10115` | `Lieferung nach 10115 Berlin` | 匹配 |
| `10115` | `Lieferung nach 101150 Berlin` | 不匹配 |
| `00-001` | `Dostawa do 00-001 Warszawa` | 匹配 |
| `00-001` | `Dostawa do 00001 Warszawa` | 匹配 |
| `111 22` | `Leverans till 111 22` | 匹配 |
| `111 22` | `Leverans till 11122` | 匹配 |

**边界**：目标为空字符串时返回 False。

### 函数三：`postal_values_equal(left, right)` —— 两个邮编值是否等价

- 两者都规范化后直接比较是否相等。
- 用于「输入框里的值」与「目标邮编」的比对。

## 测试

新建 `tests/test_postal_codes.py`，覆盖：

- 规范化函数的各种输入（含零宽字符、连字符、全角空格、None、空串）
- `postal_matches` 上表中的**全部**用例，逐条断言
- `postal_values_equal` 的等价与不等价用例
- 至少一条「部分匹配必须失败」的用例（如目标 `10115` 对读回 `101150`）

## 本模块完成标志

- 新文件存在且三个函数齐全。
- 新测试文件通过。
- 完整套件通过。
- CHANGELOG 已追加一条。
- 已提交，未推送。
- **扫描器尚未接入本模块**（M2、M3 才接入），本模块不改变任何现有行为。

# 模块 M2：页头配送读回改用规范化比对

## 目标

把「配送设置是否生效」的最终校验，从正则匹配改为 M1 提供的规范化比对，消除英国站等站点的误判。

## 依赖

M1 必须先完成。

## 背景

当前实现要点：

- 构造正则时把目标邮编按空格切开，用 `\s+` 连接，要求中间有空白。
- 先「等页头元素可见」（最多 5 秒），再「等文本匹配正则」（最多 5 秒）。
- **这两个等待的失败都被静默吞掉**（捕获断言异常后直接跳过），导致白等 10 秒，却分不清是「页头没更新」还是「页头元素根本没显示」。
- 最后再读一次文本，用正则搜索判断是否包含目标邮编。

## 改动内容

文件：`app/monitoring/adapters/playwright_scanner.py`

### 改 1：引入 M1 的工具

在文件顶部导入 `postal_matches`。

### 改 2：替换页头读回的判断逻辑

把「构造正则 + 正则搜索」替换为「调用 `postal_matches(读回文本, 目标邮编)`」。

**保留**现有的等待步骤和超时时长（可见 5 秒），但要注意：

- 原来的「文本匹配」步骤用的是 `expect(...).to_have_text(正则)`。**这一句要改掉**，因为它依赖正则。改成用 `postal_matches` 判断。
- 建议改为：等元素可见（最多 5 秒）→ 读文本 → 用 `postal_matches` 判断。
- **删除**「等文本匹配」那一步（5 秒），因为它建立在正则之上。改为直接读文本后判断。

这样每轮配送的等待时间从最多 10 秒降到最多 5 秒，且失败原因清晰。

### 改 3：失败信息要能区分两种情况

现在失败只有一句「requested delivery postal code not observed」。改成能区分：

- 页头元素不存在或不可见 → 信息里说明「页头配送栏未显示」
- 页头元素可见但内容不含目标邮编 → 信息里说明「页头仍显示：<读到的文本>」

**做法**：读回后先判断元素是否可见，再判断内容是否匹配，两种情况给不同的错误原因串。

已有的 `details` 字典里 `delivery_text_after` 已经记录了读到的文本，直接用上。

## 测试

更新 `tests/test_playwright_scanner.py`：

- 现有针对配送读回的测试保持通过。
- 新增：页头显示 `London SW1A1AA`（无空格）时，**判定为配送成功**，不返回错误。
- 新增：页头显示 `London SW1A1AB`（错误邮编）时，**判定为配送失败**。
- 新增：页头元素不存在时，错误信息里能看出是「未显示」而不是「内容不符」。

## 本模块完成标志

- 扫描器不再使用正则匹配邮编。
- 英国站无空格邮编能被正确识别为成功。
- 完整套件通过。
- CHANGELOG 已追加。
- 已提交，未推送。

# 模块 M4：配送弹窗改为等待元素出现

## 目标

把配送弹窗的打开等待，从「固定死等 1.5 秒」改为「等待邮编输入框真正出现」，消除弹窗渲染慢时的误判，同时不让正常情况变慢。

## 依赖

M1 必须先完成（改 5 需要用 `postal_values_equal`）。

## 背景

当前流程：

```
点触发器（超时 10 秒）
  ↓
固定死等 1.5 秒        ← 不检查弹窗是否真的打开
  ↓
存「弹窗打开」截图
  ↓
两级查找邮编框（全是瞬时查询，无任何等待）
```

**问题**：Amazon 的配送弹窗是 JS 动态渲染的。如果 1.5 秒内没渲染完：

- 主选择器找不到 → 走兜底查找
- 兜底也找不到 → 报「邮编框未找到或不可见」
- 但真实原因是「还没渲染完」，**错误信息把排查方向带偏**

**为什么延长死等不是解法**：延长到 3 秒只是把问题从「1.6 秒时失败」挪到「2.6 秒时失败」，本质没变。

## 改动内容

文件：`app/monitoring/adapters/playwright_scanner.py`

### 改 1：删掉固定死等

移除「点触发器之后固定等 1.5 秒」这一步。

### 改 2：改为等待邮编输入框出现

点触发器之后，改为：

```
等邮编输入框可见，最多 8 秒
```

**关键实现要求**：

- 必须用「等待元素可见」的方式，不是「先等固定时长再查」。
- 元素在等待期间出现就**立即返回**，不等满 8 秒。
- 8 秒内没出现 → 走现有的「找不到邮编框」失败分支（错误信息、诊断截图、关闭弹窗）。

**为什么是 8 秒**：配送弹窗要渲染国家下拉等复杂内容，比 Cookie 面板慢。但整个配送流程有 20 秒总闸，8 秒占 40%，所以不能再放宽。

### 改 3：诊断截图的时机调整

现在「弹窗打开」的截图是在死等之后拍的。改成：**在等待邮编框成功之后**再拍，这样截图一定反映了弹窗的真实状态（而不是「可能还没打开」）。

保留原有的「改之前」截图。失败分支仍需拍「失败」截图。

### 改 4：兜底查找层补可见性校验

当前「按属性关键词匹配」那一层**不检查可见性**，可能返回一个隐藏元素。

改为：**属性匹配命中后，必须确认该元素可见**，不可见则继续找下一个候选。

「按结构兜底」那一层已经检查了可见性，保持不变。

### 改 5：避免清空输入框时的无谓等待

当前填邮编前会先「清空输入框」，这一步用的是一次性填充语义，超时 5 秒。实测这个操作可能挂在 Amazon 的输入校验上，白等 5 秒。

改为：

- **先读取输入框当前值**。
- 如果当前值已经等于目标邮编（用 M1 的 `postal_values_equal` 做规范化比较），**跳过清空和输入**。
- 否则才执行清空 + 逐字输入。

这样在「框里已经有正确值」的场景下完全省掉两次可能挂起的操作。

**注意**：清空 + 输入这一步的超时保持现状，不要在这一模块改动等待时长策略。

## 测试

更新 `tests/test_playwright_scanner.py`：

- 新增：邮编框延迟出现（在等待窗口内才渲染）→ **能够找到并继续**，而不是报「找不到邮编框」。
- 新增：邮编框始终不出现 → 判定失败，且错误信息仍是「找不到邮编框」。
- 新增：属性匹配命中一个隐藏元素 → **跳过它**，找到后面那个可见的。
- 新增：输入框已有正确值 → 跳过清空和输入。

## 本模块完成标志

- 代码里不再有「固定死等 1.5 秒」。
- 等待策略是「等元素出现，最多 8 秒」。
- 兜底查找层有可见性校验。
- 完整套件通过。
- CHANGELOG 已追加。
- 已提交，未推送。

# 模块 M5：Cookie 等待延长并留痕

## 目标

把 Cookie 弹窗的等待从 2 秒延长到 6 秒（出现立即点击），并在等待失败时留下诊断痕迹，不再静默放弃。

## 背景

当前 Cookie 处理分两处调用（进页面后一次、详情页就绪后一次），用同一个方法：

```
等拒绝按钮可见，最多 2 秒
  ├─ 超时 → 直接返回（静默，无错误码、无截图、无日志）
  └─ 找到 → 点击（超时 5 秒）→ 等它消失（超时 5 秒）
```

**问题一：2 秒太短**。Amazon 首次访问的 Cookie 面板常在 3-5 秒后才渲染（尤其新 IP、新设备、新地区）。2 秒到了就放弃 → 弹窗残留 → 遮挡加购按钮 → 后续判定「按钮是否可用」失败。

**问题二：失败是静默的**。最终错误信息指向「加购按钮无法确认」，但真实原因是「Cookie 面板当时没找到」。**排查方向被带偏**，而且没有任何截图可查。

## 改动内容

文件：`app/monitoring/adapters/playwright_scanner.py`

### 改 1：等待时长 2 秒 → 6 秒

等 Cookie 拒绝按钮可见的最长等待改为 6 秒。**仍然是「元素出现就立即返回」**，不是「等满 6 秒再点」。

### 改 2：等待失败要留痕，但不终止扫描

等待超时后：

- 记录一个明确的诊断信息（本次 Cookie 面板未出现）。
- **继续执行后续流程**，不终止扫描。

**为什么不终止**：Cookie 面板不是每次都出现（会话内已被拒绝过、或 Amazon 直接不弹）。把它当致命错误会导致大量无谓失败。

### 改 3：诊断信息要能被最终结果看到

这个留痕不能只存在于方法内部。它必须能出现在最终扫描结果里，否则还是查不到。

**做法**：在扫描器实例上暂存一个「本次扫描的弹窗诊断列表」，每条记录包含：

- 阶段名（例如「首次访问」「商品页就绪后」）
- 发生了什么（例如「Cookie 面板未出现」「Cookie 面板已拒绝」）
- 当时页面 URL

扫描结束时，如果这个列表非空且**其中有异常项**（比如「Cookie 面板未出现」），把它附加到扫描结果的错误信息里。

**注意**：如果最终判定是 healthy 或 inventory_risk（业务判定成立），诊断信息只作为**附加信息**记录，不改变判定结果。但如果判定是 technical_failure，诊断信息要**放在错误信息的前面**，让排查第一眼就能看到。

### 改 4：点击后等消失失败的语义

点击拒绝按钮后等它消失（5 秒）失败时，当前会抛异常导致整段弹窗处理失败。

改为：**记录诊断信息，继续执行**。理由同上：Cookie 面板没关掉会在后续环节暴露出来（按钮探测失败），没必要在这里直接终止。

## 测试

更新 `tests/test_playwright_scanner.py`：

- 新增：Cookie 按钮在 3 秒后才出现（原先 2 秒会漏）→ **能够被点击**。
- 新增：Cookie 按钮始终不出现 → 扫描**不因此失败**，且诊断信息里能看到「Cookie 面板未出现」。
- 新增：Cookie 按钮点击后不消失 → 扫描不因此失败，诊断信息可查。
- 现有 Cookie 相关测试保持通过。

## 本模块完成标志

- Cookie 等待时长为 6 秒，且是「出现即点」。
- 等待失败有诊断记录，且不终止扫描。
- 诊断信息能在最终扫描结果里看到。
- 完整套件通过。
- CHANGELOG 已追加。

# 模块 M6：弹窗处理流程顺序重排

## 目标

重排弹窗处理顺序，消除「落在中间页无法自愈」这一类失败，并简化首页判定逻辑。

## 依赖

M4、M5 必须先完成。

## 背景

当前顺序：

```
导航
 ↓
① 点「继续购物」
 ↓
② 点「拒绝 Cookie」
 ↓
③ 检查当前 URL 是否是同站首页
 ↓    ├─ 是 → 重新访问商品 URL → 再点一次「继续购物」
 ↓    └─ 否 → 什么都不做
 ↓
④ 等详情页就绪
```

**问题一：URL 检查在 Cookie 之后，不在点击「继续购物」之后。**

从「点完继续购物」到「检查 URL」之间，如果页面落在一个**既不是首页也不是商品页**的中间页，首页判定为假，**不会重开商品页**。后续等详情页标题必然超时。

**问题二：首页判定只认「同域根路径」一种形态**，不认其他非商品页。

**问题三：点击「继续购物」后不验证是否回到了目标商品**（域名 + ASIN 都没校验）。

## 改动内容

文件：`app/monitoring/adapters/playwright_scanner.py`

### 改 1：新顺序

```
导航
 ↓
① 点「继续购物」
 ↓
② 无条件重新访问商品 URL
 ↓
③ 等 Cookie 弹窗（≤6 秒）→ 点 → 等消失
 ↓
④ 等详情页就绪
```

### 改 2：② 无条件重进商品 URL

**不判断当前是否在首页**，直接重新访问商品 URL。

**理由**：点「继续购物」后只有两种落点 —— 目标商品页，或同站首页。

- 已经在商品页 → 再访问一次同一 URL 是**幂等**的，最多多花一次网络往返
- 在首页 → 重新访问正是需要的修复

**一个动作覆盖两种情况**，逻辑更简单，且不再依赖脆弱的「首页判定」启发式。

**代价**：每个商品多一次导航（DE 站约 1-3 秒；40 商品 3 并发，单轮多约 30-40 秒）。已确认接受。

### 改 3：删除首页判定逻辑

`_is_marketplace_home()` 这个辅助函数，**在扫描流程里不再有调用点**，直接删除该函数。

### 改 4：保留重开时的导航中断恢复

重新访问商品 URL 时，如果抛出「导航被另一个导航中断」或「ERR_ABORTED」这类错误 —— **现在的逻辑是「只有在同站首页时才恢复」**。由于不再做首页判定，改为：

- 遇到上述两类导航中断错误 → 等页面加载完成（最多 5 秒）→ **再试一次**。
- 只有一次恢复机会。
- 其他异常照常抛出。

**保留这个恢复能力**，它是有价值的（亚马逊自己会跳转导致导航中断，实测遇到过）。

### 改 5：② 之后不再点第二次「继续购物」

当前流程在重开商品页后会**再点一次「继续购物」**。改为：重新访问商品 URL 之后**直接进入 Cookie 处理**，不再点「继续购物」。

**理由**：重新访问商品 URL 就是为了拿到真正的商品页，此时「继续购物」拦截页已经不存在，再点一次是多余动作，且可能误点到页面上其他「继续购物」文案。

### 改 6：Cookie 处理位置

Cookie 处理从「点继续购物之后」移到「重新访问商品 URL 之后」。

**理由**：Cookie 面板在**商品页**才出现；在错误页面上等 Cookie 是浪费 6 秒等待。

## 测试

更新 `tests/test_playwright_scanner.py`：

- 新增：点击「继续购物」后页面落在**中间页**（既非首页也非商品页）→ **仍然能自愈**（因为无条件重进商品 URL）。
- 新增：点击「继续购物」后落在首页 → 能自愈。
- 新增：点击「继续购物」后已经在商品页 → 能正常继续。
- 新增：重新访问商品 URL 时抛出 `net::ERR_ABORTED` → **能恢复**（等一次再试）。
- 现有弹窗相关测试保持通过。

## 本模块完成标志

- 流程顺序符合本模块「改 1」所述。
- `_is_marketplace_home()` 已删除。
- 导航中断恢复能力保留。
- 完整套件通过。
- CHANGELOG 已追加。
- 已提交，未推送。

# 附录：本次规范涉及的判断依据

供后续维护者理解为什么这样设计。

## 为什么 Cookie 等待 6 秒

Amazon 的 Cookie 面板是客户端 JS 渲染，且首访场景要下载并执行较多脚本。实测常在 3-5 秒后才出现。2 秒偏短。6 秒是在「慢网络也能覆盖」和「不拖慢正常情况」之间的折中：元素一旦出现就立即点击，正常情况不受这个上限影响。

## 为什么配送弹窗等 8 秒

配送弹窗内容比 Cookie 面板复杂（要渲染国家下拉、邮编校验逻辑等）。但整个配送流程有 20 秒总闸，8 秒已占 40%，不宜再放宽。

## 为什么用「等元素出现」而不是「延长死等」

固定死等的时间值是个猜测，且必然存在「刚好差一点」的失败区间。等待具体元素是「以实际状态为准」，没有猜测成分。代价是最坏情况多等几秒。

## 为什么无条件重进商品 URL

点「继续购物」的落点只有两种，无条件重进用一个动作覆盖两种情况，消除了「中间页」这一类无法自愈的失败，也不再需要脆弱的首页启发式判定。代价是每次多一次导航。

## 为什么邮编比对用规范化 + token 相等

- 去空白、去连字符、去零宽字符 → 覆盖 Amazon 各种显示格式差异（`SW1A 1AA` / `SW1A1AA` / 带零宽字符）。
- token 相等而非子串包含 → 防止部分匹配（目标 `10115` 误配 `101150`）。
- 不用正则 → 正则要求「中间至少一个空白」这类硬性假设，正是本次英国站误判的根因。

## 为什么配送失败不终止、Cookie 失败不终止

配送失败会终止，是因为**配送地直接决定加购按钮的判定结果** —— 配送地不对，结论就是错的，必须失败并留证。

Cookie 失败不终止，是因为它**不直接决定判定结果**。Cookie 面板没关掉会在后续环节暴露（按钮探测失败），提前终止只是把一个信息丰富的失败换成了一个信息贫乏的失败。
