# MVP 操作可靠性设计：防重复点击与消息反馈

## 1. 目标

当前 MVP 通过商品表格手动触发扫描和告警复查。用户确认本轮优先解决“按钮操作不重复、不卡住”，因此本设计只增强页面操作反馈和恢复能力，不改变扫描业务状态机。

目标是让每次操作都有明确的开始、成功、失败和可重试状态：

- 点击扫描后立即进入处理中，禁止同一商品重复提交。
- 请求成功、业务冲突、网络错误和超时都给出可理解的消息。
- 无论请求如何结束，按钮都能恢复到可操作或明确的重试状态。
- 保留后端现有的 `409` 并发保护，防止绕过浏览器按钮锁的重复请求。

## 2. 范围

### 本轮包含

- 商品扫描按钮的逐商品操作锁。
- 扫描按钮的处理中、成功、失败和重试显示。
- 统一 Toast 消息反馈，并支持键盘和屏幕阅读器感知。
- 请求超时控制，超时后释放按钮并提示重试。
- 复查按钮的同样防重复和反馈行为。
- 保持页面现有的商品状态、告警状态和演示结果切换逻辑。

### 本轮不包含

- 真实 Playwright 截图、OCR、Kafka、MySQL 或定时调度。
- 服务端持久化操作记录和跨刷新恢复。
- 全局扫描队列、批量操作和后台任务系统。
- 改变 `healthy`、`inventory_risk`、`technical_failure` 的业务含义。

## 3. 现状与约束

- 页面位于 `app/mvp/templates/index.html`，目前由浏览器脚本直接调用扫描和复查接口。
- 扫描接口已经在同一商品扫描进行时返回 `409`。
- 扫描完成后页面会重新拉取商品、扫描和告警数据。
- MVP 使用内存存储，刷新页面不会保留前端操作锁，因此前端不能假设锁状态跨刷新存在。

## 4. 方案比较与决定

### 方案 A：前端操作锁 + 超时恢复（已选择）

每个商品独立维护操作状态。点击后立即锁定当前按钮，请求在统一超时窗口内执行；请求完成、失败或超时都通过 `finally` 释放锁。服务端 `409` 作为第二道并发保护。

这是当前 MVP 的选择，因为改动集中在页面交互，能够解决重复点击和按钮永久禁用，同时不引入新的持久化模型。

### 方案 B：增加服务端操作记录

为每个操作生成 ID，并将开始时间、结束时间和状态保存到服务端，页面刷新后恢复按钮状态。本方案可靠性更高，但需要扩展内存模型、接口和测试，超出本轮目标。

### 方案 C：全局操作队列

所有扫描进入单队列，前一个操作完成后才执行下一个。它能限制并发，但会让不同商品之间互相等待，不适合当前手动演示。

## 5. 交互设计

### 5.1 扫描按钮状态

按钮文案保持动作一致：

| 状态 | 按钮显示 | 行为 |
| --- | --- | --- |
| 可操作 | 立即扫描 | 可点击 |
| 请求中 | 扫描中… | 禁用当前商品的扫描按钮，显示忙碌标识 |
| 成功 | 立即扫描 | 恢复按钮，刷新该商品状态 |
| 失败/超时 | 重试扫描 | 恢复按钮，保留当前数据并提示失败原因 |
| `409` | 扫描中… | 提示该商品已有扫描进行中，刷新数据后恢复 |

操作锁以商品 ID 为粒度，不影响其他商品的按钮。

### 5.2 复查按钮状态

复查按钮点击后立即禁用，文案变为“验证中…”。成功后重新加载告警列表；失败或超时后恢复为“重新验证”，并提示可再次操作。

### 5.3 消息反馈

页面右下角提供一个 Toast 容器，消息包括：

- 开始：`已开始扫描：{商品名}`。
- 成功：`扫描完成：{商品名}`。
- 库存风险：`发现未识别到加购入口，已创建告警`。
- 技术故障：`扫描失败：{错误原因}`。
- 冲突：`该商品正在扫描，请稍候`。
- 超时：`扫描超过等待时间，请重试`。
- 复查成功：`复查完成，告警状态已更新`。

Toast 不作为唯一反馈；按钮文案和商品状态也同步更新。错误消息使用 `role="alert"`，成功消息使用 `role="status"`，并支持自动消失和手动关闭。

## 6. 视觉与可访问性方向

页面保持运营监控工具的克制风格，不增加装饰性动效。采用以下小型设计令牌：

- 背景：`#F4F6F8`；内容面板：`#FFFFFF`。
- 主操作：`#2457D6`；处理中：`#8A5B00`；成功：`#18794E`；错误：`#B42318`。
- 正文使用系统无衬线字体；操作状态使用清晰的句式，不使用全大写标签。
- Toast 固定在右下角，移动端改为底部全宽；不遮挡当前操作行。
- 所有按钮保留可见键盘焦点；颜色之外同时使用文字表达状态。
- 遵守 `prefers-reduced-motion`，处理中只使用轻量状态变化，不使用持续跳动动画。

页面结构保持左对齐：标题区、汇总区、商品表格、告警表格。商品行中的状态和按钮是主要操作区域，Toast 只承担跨区域的即时反馈。

## 7. 请求与恢复规则

- 每个操作使用一个独立的超时计时器，建议初始值为 10 秒。
- 请求完成后先更新数据，再释放按钮锁，避免用户在旧数据仍显示时再次点击。
- `409` 不创建新的告警，也不覆盖当前商品状态；提示并刷新数据。
- 网络错误、非预期响应和超时都释放按钮锁，按钮显示“重试”。
- `finally` 是释放锁的唯一出口，避免成功和失败分支遗漏解锁。
- 用户刷新页面后以服务端返回的 `scanning` 状态为准；MVP 不承诺恢复浏览器内未完成的请求。

## 8. 验收与测试

至少验证以下行为：

1. 连续快速点击同一商品的扫描按钮，只发送一次请求。
2. 点击一个商品时，其他商品仍可操作。
3. 成功扫描后按钮恢复，商品状态和 Toast 与结果一致。
4. `409`、网络错误和超时都会显示消息并恢复按钮。
5. 复查按钮不会重复提交，失败后可以重试。
6. 键盘可以聚焦和触发按钮；错误 Toast 可被辅助技术读取。
7. 现有 MVP 单元测试继续通过，健康检查仍返回 `mode=demo`。

## 9. 后续可选增强

如果实际演示中仍出现刷新后误操作，再进入方案 B：增加服务端操作记录和操作 ID。这个决定不在本轮实现中提前引入。
